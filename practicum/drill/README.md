# Тренажёр повторения

Практикум учит приёму. Тренажёр держит его в рабочем состоянии: короткие
задания вперемешку по всем темам, с секундомером и журналом.

Открывается вкладкой «Повторение» на math.archik.tech — состояние живёт
на сервере, и с телефона работает то же самое. Локально нужны две команды:

    python practicum/drill/server.py                       # служба, порт 8042
    npm --prefix classification/web run dev                # страница, 5173

Vite проксирует `/api/drill` на 8042, всё остальное `/api` — в атлас.

## Что здесь чем занимается

| файл | что делает |
| --- | --- |
| `build_bank.py` | собирает `bank.json` из ноутбуков, генераторов и карточек |
| `codes.yaml` | связь кодов тренажёра с приёмами карточек, руками |
| `bank.json` | собранный банк: практикумы, приёмы, условия на узнавание |
| `items/` | генераторы задач на счёт, по одному модулю на практикум |
| `check.py` | разбор написанного от руки ответа и вызов проверок `kit` |
| `engine.py` | что показать следующим |
| `store.py` | журнал попыток, sqlite |
| `server.py` | шесть ручек под `/api/drill/` |

Страница живёт в атласе: `classification/web/src/components/DrillView.tsx`.

## Начальный экран

Сессия собирается до её начала, а не подстраивается по ходу:

| настройка | что делает |
| --- | --- |
| режим | вперемешку, только узнавание, только счёт |
| темы | какие практикумы берём; число на плитке — сколько в теме заданий **в этом режиме**, пустые темы отключены |
| длина | 10, 20, 40 или без конца; на последнем задании кнопка становится «итог» |
| порядок | по расписанию, сплошь, наугад |
| только просроченное | берём лишь то, чему подошёл срок; если срок не подошёл ничему, набор берётся целиком |
| секундомер | показывать или нет; время записывается в любом случае |

Настройки лежат в `localStorage`, так что второй раз собирать их не нужно.
После сессии показывается итог: счёт, время на задание и список приёмов,
где были ошибки, — они вернутся завтра, потому что ошибка сбрасывает срок.

**Порядок** стоит различать. `по расписанию` — обычный режим повторения:
вес по доле баллов, просрочке и ошибкам. `сплошь` — сплошной проход, реже
виденное вперёд, при равенстве снизу лестницы вверх: так закрывают пробелы
в новой теме, а не повторяют старую. `наугад` — поровну, без расписания.

## Три решения, на которых всё держится

**Планируется приём, а не задача.** Задача — расходный материал: в режиме
счёта она собирается заново по зерну, и запас не кончается. Планировать
задачи значило бы вести банк руками, и он бы протух.

**Вся логика на сервере, страница только рисует и меряет время.** Второй
экземпляр правил — на JavaScript — разошёлся бы с практикумами через
месяц, и `verify_drill.py` перестал бы быть правдой.

**Проверяет тот же `kit`, что и практикумы.** «Верно» в тренажёре и «верно»
в ноутбуке означают одно и то же: `2sqrt(6)` и `sqrt(24)` — один ответ,
а `29.4` вместо `12sqrt(6)` не проходит там, где просят точное значение.

## Как считается, что показать следующим

    вес = доля баллов практикума × просрочка × (1 + доля ошибок)

Доля баллов взята из карточек: практикум на 222 балла архива весит больше,
чем на 83. Просрочка растёт по ящикам Лейтнера — 0, 1, 3, 7, 21 день;
верный ответ поднимает на ящик, неверный возвращает в начало. Приём, ни
разу не показанный, идёт впереди всего остального.

Темы перемешиваются намеренно: подряд по одной учить приятнее, но именно
это даёт ложное чувство усвоенного — на экзамене задача приходит без
подписи, из какого она практикума.

## Что показывается после ответа

Разбор разложен по подписанным частям, чтобы их не путали между собой:

| подпись | что это | когда |
| --- | --- | --- |
| — | вердикт проверки из `kit`, дословно | всегда |
| `верный ответ` | эталон | при ошибке |
| `приём` | как называется и из какого практикума | всегда |
| `узнаётся по` | `trigger` карточки: по какому признаку опознают | всегда |
| `ход` | `chain` карточки: как приём выполняют, по шагам | всегда |
| `где срезаются` | `traps` карточки: типичные ошибки | при ошибке |

Ход показывается и при верном ответе — чтобы было с чем сравнить свой:
сойтись в ответе можно и длинной дорогой, а на экзамене это стоит времени.
Ловушки при верном ответе только отвлекают, поэтому приходят с ошибкой.

Всё это лежит в карточках приёмов и попадает в банк при сборке; отдельного
текста для тренажёра не пишется.

## Что меряется

Время до первого нажатия и время до отправки — отдельно. Первое показывает,
узнан ли приём; второе — насколько быстро идёт счёт. Это и есть причина
делать тренажёр страницей, а не ноутбуком: в клетке такого не измерить.

## Как добавить практикум

1. Дописать раздел в `codes.yaml` — коды тренажёра и приёмы, на которые
   они показывают.
2. `python practicum/drill/build_bank.py` — условия на узнавание банк
   возьмёт из ноутбука сам.
3. Завести `items/<id>.py` с генераторами задач на счёт и подключить его
   в `items/__init__.py`. Без этого практикум работает только на узнавание,
   и это видно в статистике.
4. `python practicum/drill/tests/verify_drill.py` — обязательно. Генератор
   задач опаснее, чем его отсутствие: он способен уверенно и бесконечно
   учить неверному.

## Режим разбора письменной работы

Четвёртый режим тренажёра, рядом с перемешкой, узнаванием и счётом.
Задание выдаёт тот же планировщик — настоящий вопрос архива по приёму,
которому подошёл срок, — страница билета показывается картинкой из PDF.
Решаешь на бумаге, по-английски, фотографируешь — и получаешь две оценки, которые никогда
не смешиваются: **математика** и **оформление**. Можно решить безупречно
и потерять три балла на записи; единая оценка это бы спрятала.

**Опора — подлинник.** Страница билета и страница схемы оценивания
рендерятся из PDF архива (`archive.py`, PyMuPDF) и уходят в модель
картинками.

Какая именно страница — определяется **по самому вопросу**, а не по
подсказке корпуса: номера страниц там шумят на единицу, причём непостоянно
даже внутри одной бумаги. Подсказка берётся ориентиром, а страница ищется
по строке, начинающейся с номера вопроса. Это исправило первую страницу
у 158 вопросов из 332 и у 66 схем оценивания. Следующая страница
добавляется только если вопрос на неё действительно продолжается —
раньше она добавлялась всегда, и в 92% случаев это была чужая страница. Пересказ из корпуса для этого не годится: он получен
извлечением и в одном доказанном случае неверен. Модель смотрит на то же,
на что смотрит экзаменатор, и в разборе цитирует его формулировки.

**Правила берутся из первоисточника.** В начале каждой схемы оценивания
напечатан раздел «Instructions to Examiners» — что означают M, A, R и AG,
когда A-балл зависит от предыдущего M, нужно ли повторять напечатанную
строку в «show that». Он есть во всех пятидесяти схемах архива, всегда
со страницы 3, и уходит в запрос текстом (около 2,5 тысяч токенов;
картинками было бы впятеро дороже, а чертежей там нет).

Инструкции объявлены **старше рубрики**: где рубрика требует большего,
чем IB, побеждают инструкции. Чтение этих страниц уже окупилось — нашлось,
что пункт `ag_final_form` требовал повторять AG-строку, а IB прямо пишет,
что этого не нужно.

**Рубрика сверена с инструкциями построчно.** Чтение всех пяти страниц
нашло четыре расхождения и четыре пробела: пункты обещали потерю «AG-балла»,
которого не существует (AG — пометка «ответ дан в условии», за него баллов
не начисляют); требовалось округлять только в самом конце, хотя IB разрешает
брать 3 з.ц. в следующий пункт; не были описаны упрощение окончательного
ответа (§8), запись калькулятора в ответе (§7), правило «зачёркнутое не
проверяется, из двух ответов считается первый» (§10) и запрет на другой
метод после «Hence» (§6). Последнему противоречила и системная роль —
она велела не наказывать за зачёркивания.

**Рубрика оформления задана явно** — `presentation.yaml`, 32 пункта:
общие, по типу вопроса («show that») и по практикумам. У каждого пункта
есть код теряемого балла и **готовая английская фраза**, которую следовало
написать. На вкус модели ничего не оставлено.

Самая строгая рубрика у A7: база проверена явно, предположение названо,
шаг отталкивается от предположения, доведён до нужной формы, и написан
вывод со ссылкой на принцип индукции — последний пункт стоит R1 и теряется
чаще всего в теме.

**Работа принимается снимками и PDF.** Телефоны складывают несколько
страниц в один файл, поэтому PDF уходит на сервер как есть и там
разбирается постранично тем же PyMuPDF, что рендерит архив — тащить
в браузер pdf.js незачем. В журнале сохраняется присланное, а не
перерисованное.

Пока идёт разбор, на странице тикает счётчик: он занимает десятки секунд,
и без него непонятно, работает проверка или страница повисла. После
вердикта показывается, сколько это стоило — время и расход токенов.

**Формулы в разборе рендерятся.** Модель просят писать математику в LaTeX
между долларами, и страница показывает её формулами, а не строкой символов.
Транскрипция — исключение: она обязана показывать лист как написано,
символ в символ, и разметки в ней быть не должно.

**Ответ модели** приходит строгим JSON, и первым полем идёт транскрипция:
проверяющий, неверно прочитавший почерк и на этом основании отчитавший,
хуже отсутствующего. Дальше — математика, оформление по пунктам, баллы
с кодами, и последним — твоё же решение, переписанное экзаменационным
языком.

**Длина сессии другая.** Одно задание — минуты, а не секунды, поэтому
в этом режиме предлагается 1, 3 или 5 работ, и бюджет времени считается
от цены вопроса: полторы минуты на балл (на бумаге пишут медленнее, чем
набирают). В перемешку разбор не подмешивается намеренно.

**Всё сохраняется.** Снимки и сканы ложатся на диск рядом с журналом
**до** отправки на проверку, а не после: если модель не ответит, работа
всё равно останется — и в списке будет видно, что разбор не состоялся
и почему. Вердикт хранится целиком, в JSON.

Раздел «мои работы» на экране настроек: список с датой, ссылкой на бумагу
и оценкой, а внутри — сами страницы и весь разбор. Файлы отдаёт ручка
`/api/drill/file`, и путь проверяется на выход за каталог снимков.

**Счёт отдельный.** Письменные работы лежат в своей таблице и в ящики
Лейтнера не идут: там измеряется скорость узнавания, здесь — качество
записи. Это разные навыки.

Ключ проверяющей модели служба читает из файла (`DRILL_GRADER_KEY_FILE`),
в репозитории его нет и в командной строке процесса он не появляется.

## Чем проверяется ответ

Каждый вид ответа уходит в свою проверку из `kit` — ту же, что стоит
в практикумах:

| вид | проверка | где встречается |
| --- | --- | --- |
| `num` | `check_num` | три значащие цифры |
| `exact` | `verify_exact` | «точное значение», десятичная не проходит |
| `expr` | `check_expr` | выражение через букву |
| `series` | `check_series` | разложения A3 |
| `set` | `check_set` | наборы значений |
| `roots` | `verify_root_set` | корни: подстановкой в само уравнение |
| `roots_in` | `verify_roots` + точный пересчёт | корни на отрезке, C3 и C4 |
| `solution_set` | `verify_solution_set` | неравенства A8, ответ множеством |
| `equation` | `verify_equation` | ответ — само уравнение |
| `identity` | `verify_identity` | «выразите через», проверка в точках |
| `factored`, `apart` | `verify_factored`, `check_apart` | форма записи A4 |
| `complex`, `complex_set` | `check_complex`, `check_complex_set` | A5 и A6 |
| `ode` | `verify_ode` | E7: подстановкой в уравнение, эталона нет |
| `triangle` | `verify_triangle` | C1: достраиванием треугольника |
| `count` | целое число | «сколько корней», «сколько треугольников» |

Ответ разбирается так, как его пишут от руки: `2sqrt(6)`, `2√6`, `x^2`,
`1, 4`, `нет`, `x < -2 or x > 3`, `-2 <= x <= 3`.

## Чего тренажёр не проверяет

Доказательство. В A7 и в приёме `prove_inequality` спрашивается счётное
ядро — база индукции, разность `S(k+1) − S(k)`, вынесенный множитель,
остаток от деления, — а не само рассуждение. Это записано в самих
заданиях и измерено в `verify_drill.py`.
